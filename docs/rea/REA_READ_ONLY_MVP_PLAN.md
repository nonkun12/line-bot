# REA Read-only MVP:導入計画と安全ゲート

## 目的

既存の LINE AI Secretary（`nonkun12/line-bot`）を読み取り専用で解析し、実装・テスト・設定・ワークフローの不整合を、検証可能な証拠とともに検出する REA（Reverse Engineering AI）を段階導入する。REA は修正を直接適用するエージェントではなく、統括AIが判断するための証拠生成器とする。

## 現段階の決定

- **導入方式:** read-only MVP から開始。最初の実装ではリポジトリ内容・Git履歴・テスト結果の静的解析を優先する。
- **無料条件:** 有料API、従量課金モデル、必須の有料SaaSを導入しない。ローカル実行と既存の無料枠を前提にし、無料枠・認証・接続が確認できない場合は外部サービスへフォールバックせず `BLOCKED` にする。
- **副作用:** リポジトリ、タスクキュー、Recovery AI のHOLD状態、環境設定を変更しない。解析レポートは一時領域またはCI artifactに限定する。
- **権限:** 読み取り専用。タスク実行、パッチ適用、HOLD解除、PR承認・マージ、デプロイ権限を与えない。
- **既存安全フラグ:** `AUTO_APPLY_PATCH=false` と `AUTO_DEPLOY=false` を維持する。
- **失敗時:** 入力不足、解析例外、SHA不一致、証拠不足、未登録タスク、テスト未実行は成功に変換せず `BLOCKED` または `NOT_RUN` とする。

## コンポーネント案

1. **Scanner（決定論的）**: Python標準ライブラリ、Git情報、既存テスト/設定を走査。許可対象外パスは読まず、シークレット値は出力しない。
2. **Analyzer（証拠中心）**: AST/設定/ワークフロー/テスト結果から検出候補を生成。最初のMVPはLLMなしで動作可能にし、LLMを使う場合も任意のローカル助言者に限定する。
3. **Finding schema**: `finding_id`, `category`, `severity`, `confidence`, `target_sha`, `evidence`, `root_cause_hypothesis`, `suggested_fix`, `required_tests`, `status` を記録する。証拠はパス・シンボル・行番号・検査名などに限定し、秘密値や任意の環境変数値を保存しない。
4. **Control Tower adapter**: REAの出力を非権威的な観測記録として渡す。REA単独ではタスクを登録・選択・承認できない。実行候補は既存の信頼済みカタログに独立して登録され、現在のHEADと一致する証拠が必要。
5. **Feedback**: 検証済みの結果だけを観測履歴へ戻す。未確認の仮説を成功記録や自動修正ルールに昇格させない。

## 段階的導入

### Phase 0 — 既存の安全ブロッカー解消（必須）

- Control Tower統合の未マージPR（特に #704 系列）を個別に確認する。
- ランタイムキューを信頼済みタスクカタログとして扱わない。
- キューにしか存在しないID、重複定義、パス許可リスト外の変更、HEAD変更、欠落/不正な証拠は拒否する。
- 現在のHOLDを手動承認なしで解除しない。
- 既存PRがDraftまたは未検証の間は、REAを実行タスク選択や本番Loopに接続しない。

### Phase 0 の実測結果（2026-10-19、対象SHA `6451c450bca9d31ea8f66e32f956c3d68c4b4d04`）

- ランタイムキュー: 23タスク
- 信頼済みカタログ: 4タスク
- ID一致: 0タスク
- 重複ID: キュー・カタログともに検出なし
- 判定: **現在の状態で安全境界を有効化すると、キュー内23タスクはすべて未登録として実行不可になる。これは意図した fail-closed 動作であり、回避のためにキューを自動登録してはならない。**
- 次の対応: タスクごとに指示・許可パス・既存テスト・副作用を確認し、個別レビュー済みのものだけを明示登録する。未審査タスクの自動登録やHOLD解除は行わない。

信頼境界修正PR #739 の検証スナップショット（head `a05a8da8f8010f9751638f6c5e7239c87c53b56b`）では、Pytest **1852 passed / 7 skipped**、Python syntax scan 成功、AI Code Review workflow 成功を確認した。ただしPR #739 はDraft・未マージで、親PR #704 も未マージのため、これは本番導入の承認ではない。テストのスキップ項目・レビュー内容・統合後の対象SHA一致も引き続き確認する。

### Phase 1 — オフライン/CI read-only scanner

- 解析対象と許可パスを明示し、リポジトリを変更しない。
- 決定論的チェックと既存pytestの結果を別フィールドに記録する。
- テストを実行できなかった場合は `NOT_RUN` とする。静的解析成功をテスト成功と見なさない。
- 同じHEAD・同じ入力で再実行したとき、安定した結果を返す。
- 解析例外や不完全なスキャンでは全体を `BLOCKED` にする。

### Phase 2 — Control Towerの観測連携

- Findingを観測データとして保存し、優先度・信頼度・根拠を表示する。
- 受信側でスキーマ、HEAD SHA、パス、サイズ、列挙値を再検証する。
- Findingは推奨に限定し、実行権限を付与しない。
- 既存の信頼境界とRecovery AI HOLD判定はREAの出力で上書きしない。

### Phase 3 — 限定タスク候補（別途承認が必要）

- REAが提案した修正を、そのまま実行キューへ投入しない。
- 人手レビューで修正範囲・許可パス・回帰テストを確認し、信頼済みタスクカタログに明示登録したものだけを対象とする。
- 1タスクずつ、変更前後のSHA、差分、テスト結果、セキュリティ検査を検証する。
- 自動適用、マージ、デプロイはこのMVPの範囲外。将来の変更も個別の設計・承認・検証を必須とする。

## 必須受け入れテスト

- キューだけに存在するIDは未登録として拒否される。
- 信頼済みカタログの重複ID（同一定義を含む）は拒否される。
- 証拠SHAと現在のHEADが異なる場合は実行候補を拒否する。
- HOLD中のタスクはREAの提案があってもHOLDのまま。
- 許可パス外のファイル変更、Git renameによる許可リスト回避、シンボリックリンク等の迂回は拒否される。
- シークレット文字列、トークン、環境変数値をレポート・ログに出力しない。
- 解析失敗、タイムアウト、テスト未実行、部分スキャンをPASSにしない。
- スキャン前後で作業ツリー、キュー、永続状態が変化していないことを検証する。
- 有料サービス/APIを呼び出さずにMVPの必須検査が完了することを確認する。
- マージ・デプロイが発生しないことを確認する。

## 導入判定ゲート

以下を**すべて**満たすまで、本番導入・Loopへの接続は行わない。

1. REA専用の小さなPRに実装と回帰テストが分離されている。
2. pytest、Python構文検査、ワークフロー検証、セキュリティ確認が対象SHAで成功している。
3. 失敗系テストが上記の拒否条件を実証している。
4. 解析結果に対象SHAと再現可能な証拠が含まれ、秘密情報がない。
5. 無料条件を満たし、有料サービスへの暗黙のフォールバックがない。
6. 既存Control Towerの信頼境界/HOLD/権限に回帰がない。
7. 独立レビューで重大指摘がなく、レビュー対象SHAがCI対象SHAと一致する。
8. 導入時にも `AUTO_APPLY_PATCH=false`、`AUTO_DEPLOY=false`、マージ・デプロイ禁止が維持される。

**現時点のステータス:** 計画文書のみ。REAのコード実装・実行・本番導入を意味しない。Phase 0の既存ブロッカー確認を先に進め、受け入れ条件を満たしてから段階的に導入する。
